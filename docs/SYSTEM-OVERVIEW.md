# Как устроена вся система: телефон + сервер + 1С

Дата: 2026-09-02. Пишу максимально простым языком, чтобы можно было
поддерживать и ничего не терять. Здесь — про **все технологии**, **все
запросы** в обе стороны и **что где хранится**.

Смежный документ на сервере: `lombard-server/PUSH-FLOW.md` — там очень
подробно про путь одного пуша от 1С до отчёта. Здесь — картина целиком,
включая то, что добавили батчами 2–4 (bind-status, inbox, app-log, ping,
фоновый воркер).

---

## 0. Картина за одну минуту

Есть три участника:

1. **1С** (учётная система ломбарда). Знает клиентов по `UserID` (GUID).
   Хочет слать клиенту сообщения. Умеет два канала: **push** (через наш
   сервер) и **SMS** (свой). Мы в 1С ничего не меняем — только дёргаем её
   готовые методы.
2. **Наш сервер** (`lombard.center/api/*.php`) — прослойка. Принимает от 1С
   «разошли вот это вот этим клиентам», сам общается с Google/Apple, следит
   кто получил, кто нет, кому слать SMS вместо push. Хранит всё в MySQL.
3. **Приложение** на телефоне клиента (Flutter). Регистрирует «адрес для
   push» (FCM-токен) на сервере, принимает пуши, показывает их, подтверждает
   доставку, ведёт локальную историю и журнал.

Push — это **не** гарантированная доставка. Это «звоночек». Поэтому есть
подстраховки: подтверждения доставки (ack), SMS-догонка, серверный «ящик»
(inbox) со всеми сообщениями клиента, тихие пинги для оживления протухших
токенов, фоновый воркер в приложении и централизованный журнал ошибок.

## 1. Словарь (без него дальше не понять)

| Термин | Что это простыми словами |
|---|---|
| **FCM** | Firebase Cloud Messaging — служба Google, которая доставляет пуши на Android. Бесплатная. Работает так: телефон получает у Google «адрес» (токен), отдаёт его нам, мы просим Google «доставь на этот адрес». |
| **APNs** | То же самое, но для iPhone (Apple). FCM для iOS внутри ходит через APNs. |
| **FCM-токен** | Строка ~160 символов. «Почтовый адрес» конкретной установки приложения на конкретном телефоне. Может смениться сам (переустановка, очистка данных, ~раз в год простоя, смена железа). Когда сменился — старый мёртв. |
| **device_uuid** | Наш собственный идентификатор установки. Генерим в приложении, храним в памяти телефона. В отличие от FCM-токена **не меняется**, пока приложение не снесли. По нему связываем «этот телефон» ↔ «этот клиент», даже если FCM-токен уже третий по счёту. |
| **user_id / UserID** | GUID клиента из 1С. Один клиент = один `user_id`, даже если у него два телефона. |
| **msg_id** | 32 hex-символа. Уникальный номер одного отправленного сообщения одному клиенту. По нему приложение подтверждает доставку, а сервер понимает «за что пришёл ack» и не дублирует запись в истории/ящике. |
| **id_send / ID_send** | Номер одной **рассылки** от 1С (в ней может быть много клиентов). Внутри рассылки у каждого клиента свой `msg_id`. |
| **data-only push** | Пуш без готового «заголовок+текст» от Google. Внутри только данные (`title`, `body`, `link`, `msg_id`). Само приложение решает, показывать ли уведомление и какое. Нужно, чтобы код приложения выполнялся даже когда пуш пришёл на закрытое приложение (иначе не отправить ack, не записать в историю). |
| **ack** (acknowledgement) | «Квитанция». Приложение получило пуш → дёргает сервер: «msg_id такой-то — доставлен». Ack не fire-and-forget: если POST не прошёл (обрыв связи), msg_id лежит в очереди `pending_acks` и до-сылается при старте / resume / появлении сети / syncInbox / фоновом воркере. Нет квитанции за окно → сервер **повторяет пуш** (окна 5→10→20→30 мин), и только после всех попыток без ack говорит 1С слать SMS. |
| **inbox / user_inbox** | Серверный «ящик» сообщений по каждому клиенту. Пуш мог не дойти (телефон был выключен неделю, токен сдох) — но в ящике сообщение лежит. Приложение при старте спрашивает «что я пропустил?» и забирает пачкой. |
| **outbox / push_outbox** | Серверная **очередь на отправку**. 1С кладёт задачу в очередь и сразу свободна; отдельный процесс (воркер) её разгребает. Если сервер упал на середине — задача не потеряется, доразошлётся. |
| **headless-изолят** | Кусок кода приложения, который ОС запускает **без экрана**, когда пришёл пуш или сработал фоновый таймер. Отдельная мини-копия движка Dart. Там нет UI, но можно ходить в сеть и в память. |
| **SharedPreferences** | Хранилище «ключ-значение» на телефоне (типа маленькой БД настроек). Тут лежат `phone_verified`, `verified_user_id`, `device_uuid`, история пушей, журнал и т.д. **Очистка данных приложения / некоторые «оптимизаторы» на Xiaomi это стирают** — отсюда «разлогины». |
| **MODX** | CMS, на которой сделан сайт lombard.center. Нам важно одно: файл `config.inc.php` при подключении определяет глобальные переменные (`$uuid`, `$database_*` и т.д.). Из-за этого в серверных скриптах свои переменные надо называть с префиксом (`bs_`, `ib_`), иначе MODX их перезатрёт. |

## 2. Технологии на ТЕЛЕФОНЕ (приложение)

Приложение написано на **Flutter** (язык Dart). Один код — и Android, и iOS.
Ниже — каждая библиотека/механизм: **что это**, **зачем здесь**, **что будет
если отвалится**.

### 2.1. `firebase_core` + `firebase_messaging` — приём пушей

- **Что.** Официальный SDK Firebase. `firebase_core` — инициализация (читает
  `firebase_options.dart` / `google-services.json`). `firebase_messaging` —
  сами пуши: получить токен, слушать входящие, `onTokenRefresh`.
- **Зачем.** Это единственный способ получать пуши на Android без своего
  сервера соединений.
- **Ключевые точки в коде** (`lib/services/push_service.dart`):
  - `FirebaseMessaging.instance.getToken()` — получить «адрес». Может
    зависнуть/кинуть ошибку, поэтому обёрнут в таймаут 30 с и цикл ретраев
    (3с → 10с → 30с → 90с → 4мин, всего 6 попыток).
  - `onTokenRefresh` — Google сам сообщил, что токен сменился → шлём новый
    на сервер.
  - `onMessage` — пуш пришёл, приложение открыто.
  - `onBackgroundMessage` → top-level `firebaseMessagingBackgroundHandler`
    (`@pragma('vm:entry-point')`) — пуш пришёл на свёрнутое/убитое
    приложение, ОС поднимает headless-изолят.
- **Если отвалится.** Токен не получен → клиент не получает пуши. Подстраховки:
  диагностика улетает на сервер (`fcm-log.php`), при каждом возврате в
  приложение и по сети — новая попытка, серверный inbox всё равно донесёт
  сообщения при следующем открытии, 1С через 20 мин без ack переведёт на SMS.

### 2.2. `google_api_availability` — «почему нет токена»

- **Что.** Спрашивает у Android статус Google Play Services:
  `success` / `serviceMissing` / `serviceDisabled` /
  `serviceVersionUpdateRequired` / `serviceUpdating` / `serviceInvalid`.
- **Зачем.** Токен FCM не генерится ровно тогда, когда Play Services
  сломаны/обновляются/отсутствуют. Раньше «гадали на кофейной гуще» — теперь
  этот статус уходит в диагностику на сервер, и видно причину.
- **Если отвалится.** Просто в диагностике будет `play_services: check_failed`
  — не критично.

### 2.3. `workmanager` — фоновый воркер (батч «фон»)

- **Что.** Обёртка над нативным Android **WorkManager** — системный
  планировщик фоновых задач. Задача переживает закрытие приложения и
  перезагрузку телефона; ОС сама выбирает момент (группирует с другими
  приложениями ради экономии батареи).
- **Зачем.** Раз в ~24 часа, даже если приложение не открывают:
  1. взять свежий FCM-токен и переотправить на сервер (лечит «токен
     ротировался, приложение не открывали, пуши идут в никуда»);
  2. подтянуть пропущенные сообщения из inbox;
  3. выгрузить журнал `AppLog` на сервер.
- **Точки в коде.** `lib/main.dart`: `callbackDispatcher` (top-level,
  `@pragma('vm:entry-point')`) → `Workmanager().registerPeriodicTask(...)`
  с `frequency: 24h`, `initialDelay: 15min`, `NetworkType.connected`,
  `ExistingPeriodicWorkPolicy.keep`. Сама работа —
  `PushService.runBackgroundTokenSync()`.
- **Версия зафиксирована точно:** `workmanager: 0.10.9` (не `^0.10.0`).
  Плавающая версия тянула рассинхрон с `workmanager_platform_interface` и
  сборка падала. **Не менять на `^`.**
- **Когда НЕ сработает.** Пользователь сделал «Остановить» (Force Stop) в
  настройках приложения, либо OEM-«оптимизатор» (Xiaomi/Huawei/Oppo) заморозил
  приложение целиком. На эти случаи — серверный `push-refresh-ping.php` +
  inbox.

### 2.4. `flutter_local_notifications` — показ уведомления

- **Что.** Рисует само уведомление в шторке (заголовок, текст, иконка
  «весы», канал `twa_push_channel`), ловит тап по нему.
- **Зачем.** Пуши у нас data-only → системного уведомления нет, приложение
  строит его руками. Плюс тап должен открывать нужный экран/ссылку.
- **Если отвалится.** Пуш пришёл, но уведомление не показалось. Сообщение
  всё равно попадает в локальную историю и в inbox — клиент увидит при
  открытии.

### 2.5. `connectivity_plus` — реакция на сеть

- **Что.** События «сеть появилась / пропала / сменилась».
- **Зачем.** Много чего делается «когда будет сеть»: нет токена → новая
  попытка; токен есть, но POST на сервер не прошёл офлайн → повторить.
- **Если отвалится.** Просто не будет мгновенной реакции на возврат сети —
  подхватится на следующем старте / возврате в приложение.

### 2.6. `shared_preferences` — локальное хранилище

- **Что.** Ключ-значение на диске телефона.
- **Что храним:** см. раздел 6.
- **Если сотрут** (очистка данных, MIUI, переустановка): теряется
  `phone_verified` и история. Лечится: `bind-status.php` (сервер — источник
  истины, восстанавливает флаг привязки) + `inbox.php` (доносит историю).

### 2.7. `smart_auth` — автоподстановка кода из SMS (Android)

- **Что.** SMS User Consent API от Google: система показывает диалог
  «разрешить приложению прочитать этот код?», код сам подставляется в поле.
- **Зачем.** Удобство при привязке номера. На iOS этого API нет — там код
  подставляет клавиатура (QuickType) через `autofillHints: [oneTimeCode]`.
- **Если отвалится.** Клиент вводит код руками. Не критично.

### 2.8. `url_launcher` — открытие ссылок

- **Что.** Открыть URL во внешнем браузере.
- **Зачем.** Ссылки внутри текста пуша — кликабельные (это был баг №1:
  раньше не открывались). Виджет `LinkifiedText` находит `http(s)://…` в
  тексте и делает их тапабельными.

### 2.9. `webview_flutter` — экран «Наши услуги» и «Личный кабинет»

- **Что.** Встроенный браузер внутри приложения (`MainWebViewScreen`).
- **Зачем.** «Наши услуги» открывает сайт, «Личный кабинет» —
  `https://lombard.center/onlajn-pogashenie/`. Плюс сюда же попадает клиент
  после тапа по пушу со ссылкой.

### 2.10. `appmetrica_plugin` (`AnalyticsService`) — аналитика

- **Что.** Яндекс AppMetrica: экраны, события, крэши.
- **Зачем.** Продуктовая аналитика. Инициализация обёрнута в try/catch —
  если упадёт, приложение стартует дальше.

### 2.11. `device_info_plus` / `package_info_plus` / `android_id` — «паспорт» устройства

- **Что.** Модель, версия ОС, версия приложения, производитель, ABI,
  android_id.
- **Зачем.** (а) шлём вместе с токеном (`fcm-token.php`), чтобы на сервере
  видеть парк устройств; (б) диагностика «почему нет токена»; (в)
  `device_uuid` собирается на базе стабильных идентификаторов (`utils/device_id.dart`).

### 2.12. Механизмы Flutter для ловли ВСЕХ ошибок (батч «журнал»)

`lib/main.dart`, всё внутри `runZonedGuarded`:
- `FlutterError.onError` — ошибки виджетов/рендера;
- `PlatformDispatcher.instance.onError` — асинхронные ошибки Dart;
- `runZonedGuarded(..., onError)` — всё, что просочилось мимо;
- каждая пойманная ошибка → `AppLog.event('flutter_error' | 'platform_error'
  | 'zone_error', {...})` → немедленная выгрузка на сервер.

### 2.13. `AppLog` — структурный журнал приложения (батч «журнал»)

- **Что.** Кольцевой буфер событий в `shared_preferences` (до 600 строк),
  каждая строка — `{t: время, e: имя_события, d: данные}`.
- **Как уходит на сервер.** Пачками (до 400 за раз) на
  `POST https://lombard.center/api/app-log.php`:
  - **сразу**, если событие содержит `error` / кончается на `_fail` /
    равно `token_giveup`;
  - иначе — каждые 40 событий;
  - и при уходе приложения в фон (`lifecycle_paused`);
  - и минимум раз в 6 часов.
- **Что логируется:** старт, жизненный цикл, сеть, разрешения, весь
  жизненный путь токена (`token_ok/recovered/fail/giveup/sent/send_fail`),
  приём пушей, ack, bind-status, inbox-sync, работа фонового воркера, и все
  необработанные ошибки.
- **Зачем.** Раньше логи были только в консоли разработчика (`debugPrint`) —
  с реального телефона клиента их не достать. Теперь по `install_id` /
  `device_uuid` / номеру телефона видно всю историю конкретного устройства
  на сервере (`app-log-view.php`).
- **Идентификаторы:** `install_id` (16 байт hex, генерится один раз на
  установку), `session_id` (новый на каждый запуск) — по ним склеиваются
  события.

## 3. Технологии на СЕРВЕРЕ

Хостинг shared (reg.ru/beget). **PHP 8.2**, **MySQL 5.7**, сайт на **MODX**.
Никаких фреймворков — чистые PHP-скрипты в `public_html/api/`.

### 3.1. PHP-скрипты как «эндпоинты»

Каждый файл `*.php` — это URL. Телефон/1С шлёт HTTP-запрос — скрипт
отрабатывает и отвечает JSON-ом. Некоторые скрипты запускаются **не по
HTTP, а по расписанию** (cron) — это фоновые задачи.

### 3.2. MySQL — вся память системы

Таблицы (подробно — раздел 6):
`fcm_tokens`, `push_send_package`, `push_send_recipient`, `push_send_log`,
`push_outbox`, `user_inbox`, `job_heartbeat`, `fcm_diag_log`,
`app_event_log`.

Особенности версии 5.7: **нет** `ADD COLUMN IF NOT EXISTS`, **нет** оконных
функций. Все миграции — руками в phpMyAdmin, файлы `migrate_*.sql`, **до**
заливки PHP.

### 3.3. FCM HTTP v1 API + сервис-аккаунт (OAuth)

- **Что.** Чтобы попросить Google доставить пуш, сервер шлёт
  `POST https://fcm.googleapis.com/v1/projects/lombardspb-a2919/messages:send`.
- **Авторизация.** Не «ключ в заголовке», а OAuth2: из
  `firebase-service-account.json` (приватный ключ проекта) собирается
  подписанный JWT, меняется на access-token (живёт ~1 час, кэшируем 55 мин).
  Код — `fcm.php`, `getFirebaseAccessToken()`.
- **Классификация ответа.** `fcmClassify()` разбирает ошибку Google в класс:
  `ok` / `unregistered` (приложение удалено) / `invalid` (кривой токен) /
  `transient` (временно) / `auth` (проблема с нашим сервис-аккаунтом) /
  `other`. От класса зависит, гасим токен или нет.

### 3.4. cron — фоновые задачи по расписанию

`* * * * * /opt/php/8.2/bin/php /путь/скрипт.php` — «запускать раз в
минуту». Список — раздел 5.

### 3.5. `flock` — «один экземпляр за раз»

Кроны берут файловый замок. Если предыдущий запуск ещё не закончился —
новый сразу выходит. Защита от наложения.

### 3.6. `fastcgi_finish_request()` — «ответить и продолжить работать»

1С и приложению важно получить ответ быстро. Скрипт отдаёт JSON, вызывает
`fastcgi_finish_request()` — соединение закрывается, а PHP **продолжает**
выполнять тяжёлую часть (рассылку). Клиент не ждёт.

### 3.7. MODX `config.inc.php`

Подключается ради доступа к БД (`$database_server`, `$database_user`, …).
Побочка: он **определяет глобальные `$uuid`, `$site_url` и т.п.** Поэтому в
новых скриптах локальные переменные — только с префиксом (`bs_`, `ib_`),
иначе `require config.inc.php` посреди скрипта затирает твой `$uuid`. На
этом уже один раз обожглись (`bind-status.php` возвращал `bound:false`).

### 3.8. Простые «дашборды» под паролем (`auth.php`)

`health.php` (JSON о здоровье системы), `fcm-log-view.php`,
`app-log-view.php`, `push-send-view.php`, `push-admin.php` — HTML-странички
для человека. Basic-логин через `auth.php`.

## 4. ВСЕ запросы: ТЕЛЕФОН → СЕРВЕР

Порядок — примерно как в жизни. Все — HTTPS, тело JSON (кроме inbox GET).

| # | Куда | Когда шлётся | Что отправляет | Что получает / делает сервер |
|---|---|---|---|---|
| 1 | `POST fcm-token.php` | старт приложения (получен токен), `onTokenRefresh`, возврат сети после неудачи, фоновый воркер | `token, user_id, device_uuid, platform, device_model, app_version, os_version, app_source:"flutter", push_ack:true` | upsert в `fcm_tokens` по `device_uuid` (одна строка на телефон). Сбрасывает `disabled_at`, `fail_count`. Если это первый живой токен клиента — зовёт в 1С `setpush(1)` (включить push-канал). |
| 2 | `POST fcm-token.php?action=delete` | клиент нажал «Отключить персональные уведомления» | `token, user_id, device_uuid, reason, app_source` | гасит токен, зовёт в 1С `setpush(0)` (клиента — на SMS). Приложение параллельно делает `FirebaseMessaging.deleteToken()`. |
| 3 | `POST fcm-log.php` | **каждая неудача** получения токена; «получилось, но не с первой попытки»; фоновый воркер без токена | большой JSON диагностики: `stage, attempt, device_uuid, app_version, platform, os_version, device_model, brand, play_services (!), authorization_status, auto_init_enabled, error_type, error_code, error_message, stack` | пишет строку в `fcm_diag_log` + в файловый лог. Смотреть — `fcm-log-view.php`. Это ответ на «почему у 69 из 1000 нет токена». |
| 4 | `POST push-ack.php` | при приёме любого пуша (foreground / headless / тап) + до-отправка из очереди `pending_acks` при старте/resume/сети/syncInbox/воркере | `msg_id, source` (`foreground`/`background`/`tap`/`queued`) | `push_send_log.acked_at = NOW` по `msg_id`; `fcm_tokens.push_ack=1, ack_declared=1` (устройство доказало, что умеет ack); если есть `push_send_recipient` — `status_final=1` (доставлено), `next_check_at=NULL`. В 1С сам **не** ходит — это делает крон. Идемпотентно (`acked_msg_ids` 300 + очередь `pending_acks`). |
| 5 | `POST bind-status.php` | старт приложения (после токена); экран «Уведомления», если локально `phone_verified=false` | `device_uuid, token?` | ищет в `fcm_tokens` по `device_uuid`, потом по `token`. Отвечает `{bound, push_enabled, user_id, phone (полный, желательно), phone_mask, verified_at}`. Приложение считает «привязан» ⇔ `bound=true` **И** непустой `user_id`. **Только чтение.** Приложение по ответу может ВОССТАНОВИТЬ `phone_verified` (никогда не снимает) и показать номер **без маски** (`phone`; `phone_mask` — запасной вариант) («зарегистрирован номер …»). Если привязка восстановлена — приложение сразу шлёт `fcm-token.php` уже с `user_id` (запрос 1), не дожидаясь перезапуска. |
| 6 | `GET inbox.php?user_id=&device_uuid=&since_id=&limit=100` | старт приложения, возврат в приложение (`resumed`), приход тихого пинга `token_refresh`, фоновый воркер — **только если номер привязан** | параметры в URL | проверяет, что `device_uuid` принадлежит `user_id` (`SELECT 1 FROM fcm_tokens …`). Отдаёт `{items:[{id,msg_id,title,body,link,created_at,delivered_at}], last_id}` — всё с `id > since_id` за 90 дней. |
| 7 | `POST inbox.php` | после успешного GupG inbox, если пришло новое | `user_id, device_uuid, last_id` (или `fetched_ids[]`) | ставит `fetched_at` забранным строкам `user_inbox`. |
| 8 | `POST app-log.php` | пачками: срочно на ошибках, каждые 40 событий, при уходе в фон, раз в 6 ч | `install_id, session_id, app_version, device_uuid, app_source:"flutter", events:[{t,e,d}, …]` (до 400) | вставляет строки в `app_event_log` + файловый лог. Всегда отвечает `{status:ok}`. Смотреть — `app-log-view.php`. |
| 9 | `POST 1c.php?action=getcontactid` | клиент ввёл номер, нажал «Получить код» | `phone, device_uuid` | прокси в 1С: та проверяет номер, шлёт клиенту SMS с кодом, возвращает `status` (1/2 — код отправлен; 0,3–7 — причина отказа), `user_id`, `kod`. |
| 10 | `POST 1c.php?action=binddevice` | клиент ввёл верный код | `user_id, device_uuid, phone` | 1С привязывает устройство к клиенту. Успех → приложение пишет `phone_verified=true`, `verified_user_id`, `verified_phone`. |
| 11 | `POST 1c.php?action=setpush` | клиент нажал «Отключить уведомления» (ветка с известным `user_id`) | `user_id, operation:0` | 1С переключает клиента на SMS-канал. |

**Не перегрузит ли сервер?** Нет. На один запуск приложения — это ~3–5
маленьких запросов (token, bind-status, inbox, изредка app-log). ack — по
одному на каждый реально пришедший пуш. Всё с таймаутами и защитой от
повторов (`_inboxInProgress`, `_tokenInProgress`, `acked_msg_ids`,
`inbox_last_id`). Диагностика (`fcm-log`) шлётся только когда что-то не так.

## 5. ВСЕ каналы: СЕРВЕР → ТЕЛЕФОН

Тут ровно один транспорт — **FCM push** (Google → телефон). Разница только в
содержимом `data`.

| Тип | Кто шлёт | `data` | Что делает приложение |
|---|---|---|---|
| **Персональный пуш** | воркер `push-outbox-worker.php` (задачу поставила 1С через `1c_send_push.php`) | `title, body, link, msg_id, id_send` | headless-изолят: сразу `push-ack.php`, затем запись в локальную историю (дедуп по `msg_id`), затем показ уведомления. |
| **Массовый пуш** | `push-admin.php` (человек из админки, под паролем) | `title, body, link, msg_id` | то же самое; но по нему нет `push_send_recipient`, значит нет SMS-догонки. Ack всё равно «учит» устройство (`push_ack=1`). |
| **Тихий пинг `token_refresh`** | cron `push-refresh-ping.php` | `type: "token_refresh"` (без title/body) | НЕ показывает уведомление, НЕ пишет в историю, НЕ шлёт ack. Делает `ensureToken(force:true)` → новый токен на сервер, затем `syncInbox()`, затем выгрузка журнала. Оживляет устройства, которые давно не открывали. |
| **Контентный пуш с флагом `refresh_token`** | любой отправитель, если положил в `data` `refresh_token:"1"` | `title, body, link, msg_id, refresh_token:"1"` | показывает сообщение как обычный пуш И вдобавок в фоне делает `ensureToken(force:true)` → переотправляет токен. Ручка на случай «доставка деградирует, но пуш ещё проходит». |

**Как формируется персональный пуш (кратко, детали — `PUSH-FLOW.md`):**

```
1С → POST 1c_send_push.php {Token, Content:[{UserID, Textpush}, …]}
     │  считает req_hash (sha256 тела). Если такой же был < 90 сек назад —
     │  помечает себя status='duplicate' и выходит (защита от даблов).
     │  INSERT push_send_package. Отвечает 1С {ID_send} и fastcgi_finish_request.
     │
     └─ на каждого клиента: INSERT в push_outbox (очередь), status='queued'
                            + INSERT в user_inbox (ящик), ключ user_id+msg_id
        (1С уже отключилась, это доделывается в фоне)

cron push-outbox-worker.php (раз в минуту)
     │  берёт queued-задачи
     │  INSERT user_inbox (идемпотентно — на случай если 1c_send_push не успел)
     │  берёт живые токены клиента из fcm_tokens
     │  sendFirebasePush(token, …) → Google → телефон
     │  fcmApplyResult() — политика токена (ok / disabled / kept)
     │  INSERT push_send_recipient со status_final: 0 (нет токенов/отклонил),
     │        1 (ушло на «старое» приложение без ack), NULL (ждём ack)
     │  status='done' в push_outbox
     │
     └─ по решённым (0 и 1) — сразу pushReportOneSend() → POST 1c/pushresult

приложение: пришёл пуш → POST push-ack.php {msg_id}  (или из очереди pending_acks позже)
     │  push_send_recipient.status_final = 1

cron push-reconcile.php (раз в минуту)
     ├─ кто ждёт ack и вышло окно:
     │     попытки < 4  → ПОВТОРНАЯ отправка пуша, next_check_at += (5→10→20→30 мин)
     │     попытки = 4  → status_final = 0 (ack_timeout)
     ├─ у кого вердикт готов, а в 1С не ушёл → POST 1c/pushresult
     │     Status=0 → 1С шлёт клиенту SMS (догонка)
     │     Status=1 → доставлено, всё
     └─ закрывает пакеты, у которых все получатели отчитаны
```

## 7. Фоновые задачи сервера (cron)

| Скрипт | Расписание | Что делает | Heartbeat |
|---|---|---|---|
| `push-outbox-worker.php` | раз в минуту | разгребает очередь `push_outbox`: шлёт пуши, пишет `user_inbox`, `push_send_recipient`, инлайн-отчёт в 1С | `outbox` |
| `push-reconcile.php` | раз в минуту | ждущие ack: повтор пуша с растущим окном (5→10→20→30 мин), после 4 попыток → Status 0 → SMS; поздние ack; добивка отчётов в 1С; закрытие пакетов; dead-letter при `report_attempts>=20` | `reconcile` |
| `push-refresh-ping.php` | раз в сутки (например ночью) | тихий пуш `token_refresh` токенам, неактивным > 3 дней (пачкой до 800); отдельно — «тёмные» клиенты (привязан, но 0 живых токенов, активность >2 дней) → в 1С `setpush(0)` | `refresh_ping` |
| `fcm_cleanup.php` | 04:00 | hard-delete токенов, погашенных >30 дней; гасит «висяки» >270 дней; чистит `app_event_log` >30д, `fcm_diag_log` >60д, `user_inbox` >90д | — |

**Мониторинг:** `GET health.php` — JSON `{ok, checks, problems}`, отдаёт
**HTTP 503**, если: крон-heartbeat протух (reconcile молчит >180 с), очередь
застряла, много ошибок авторизации FCM за 30 мин, не получить access-token
Google, есть dead-letter и т.д. На это можно повесить внешний аптайм-монитор
(UptimeRobot) — придёт письмо/телега при 503.

## 8. Сквозные сценарии (что за чем)

### 8.1. Клиент впервые ставит приложение
1. Старт → `Firebase.initializeApp` → `getToken()` (с ретраями).
2. Токен есть → `POST fcm-token.php` (строка в `fcm_tokens`, `user_id`
   пустой пока).
3. `bind-status.php` → `bound:false` (номер не привязан) — ок.
4. `syncInbox()` не делает ничего (нет `verified_user_id`).
5. Клиент идёт в «Персональные уведомления» → вводит номер →
   `getcontactid` (1С шлёт SMS с кодом) → вводит код → `binddevice` →
   `phone_verified=true`, `verified_user_id` сохранён.
6. Следующий `fcm-token.php` уйдёт уже с `user_id` → сервер зовёт в 1С
   `setpush(1)`.

### 8.2. 1С шлёт клиенту сообщение
См. схему в разделе 5. Итог: либо ack (Status 1) — в т.ч. поздний, после
до-отправки из очереди `pending_acks`; либо сервер 4 раза повторил пуш
(окна 5→10→20→30 мин) и всё равно нет ack → Status 0 → 1С шлёт SMS.
В любом случае сообщение лежит в `user_inbox`.

### 8.3. Клиент удалил приложение
1. 1С шлёт пуш → воркер → Google отвечает `UNREGISTERED`.
2. `fcmApplyResult()` → `disabled_at=NOW` этому токену.
3. Если это был последний живой токен клиента → `fcmMaybeDisablePushIn1C()`
   → в 1С `setpush(0)` → 1С дальше шлёт этому клиенту **SMS**, не пуш.
   (Есть защита: если токен «шевелился» < 30 мин назад — это, скорее всего,
   ротация, а не удаление; тогда `SETPUSH_0_DEFERRED`, ждём.)

### 8.4. У клиента сменился токен, приложение он не открывает
1. `push-refresh-ping.php` (ночью) шлёт тихий `token_refresh` на старый
   токен — Google ещё какое-то время доставляет на «спящую» установку.
2. Приложение в headless-изоляте: `ensureToken(force:true)` → новый токен →
   `fcm-token.php`. Строка в `fcm_tokens` обновилась (по `device_uuid`),
   старый токен ушёл.
3. Плюс фоновый воркер (`workmanager`) раз в сутки делает то же самое.

### 8.5. Клиент неделю не включал телефон, за это время пришло 3 пуша
1. Пуши не доставились (или доставились и протухли). В `user_inbox` — 3
   строки.
2. Клиент открыл приложение → `syncInbox()` → `GET inbox.php?since_id=N` →
   приходят 3 сообщения пачкой → мёржатся в локальную историю (дедуп по
   `msg_id`) → клиент видит все три в «Истории уведомлений».

### 8.6. Клиент переустановил приложение / MIUI стёр данные (разлогин) — но номер он уже подключал
1. `phone_verified` пропал. Экран «Уведомления» показывает форму ввода номера.
2. Но ещё до формы приложение шлёт `bind-status.php` по `device_uuid` (тот же,
   пока приложение не снесли начисто) и находит: `bound:true`, `user_id: …`,
   `phone_mask: …`. Приложение **восстанавливает** `phone_verified=true` и
   `verified_user_id`, показывает «✅ Персональные push-уведомления подключены»
   и «зарегистрирован номер …» — **без повторного ввода кода из SMS**.
3. Сразу же приложение до-регистрирует токен (`fcm-token.php` уже с `user_id`)
   → серверная строка токена получает владельца, сервер зовёт `setpush(1)`.
4. `syncInbox()` до-тягивает историю.
   (Отсутствие мигания шага 1→2 — это фикс с крутилкой.)

### 8.7. Google-сервисы на телефоне сломаны — токен вообще не генерится
1. 6 попыток с ретраями, каждая неудача → `fcm-log.php` с
   `play_services: serviceVersionUpdateRequired` (или др. причина).
2. `token_giveup` в журнал → срочная выгрузка.
3. При каждом возврате в приложение и при появлении сети — новый цикл
   попыток.
4. Клиент всё равно получит сообщения из `inbox` при открытии; 1С — через
   SMS.

## 9. Что может сломаться и что подстраховывает

| Точка отказа | Прямое следствие | Подстраховка |
|---|---|---|
| FCM-токен не сгенерился | нет пушей | ретраи + пинг + фоновый воркер + inbox + SMS от 1С; причина видна в `fcm_diag_log` |
| Токен ротировался, приложение не открывают | пуши в никуда | `push-refresh-ping.php` + `workmanager` раз в сутки |
| Пуш не дошёл (сеть/убито/OEM) | клиент не увидел | ack не пришёл → 1С шлёт SMS; сообщение в `inbox` |
| Стёрлись локальные данные | «разлогин», пропала история | `bind-status.php` (сервер — источник истины) + `inbox.php` |
| Сервер упал посреди рассылки | часть клиентов без пуша | `push_outbox` — очередь, задачи переживают падение, воркер доразошлёт |
| 1С прислала дубль рассылки | клиент получит 2 одинаковых | `req_hash` — дубль в пределах 90 сек отсекается |
| Ack не дошёл (обрыв связи в момент приёма) | сервер думает «не доставлено» | очередь `pending_acks` на телефоне — до-шлётся при старте/resume/сети/syncInbox/воркере |
| Устройство реально не получает пуши (OEM убил / токен протух) | клиент не увидел | сервер 4 раза повторяет пуш (5→10→20→30 мин), затем честно Status 0 → 1С шлёт SMS; сообщение в `inbox`. «Замка» больше нет — недоставка не маскируется под «доставлено» |
| Крон завис | тихо копится очередь | `flock` + `job_heartbeat` + `health.php` отдаёт 503 |
| Ошибка в приложении у клиента | не видно с той стороны | `runZonedGuarded` + `AppLog` → `app-log.php`, видно в `app-log-view.php` |

## 10. Куда смотреть по конкретному клиенту

1. **`app-log-view.php?q=<номер | device_uuid | user_id | install_id>`** —
   таймлайн событий приложения этого устройства: старты, токен, пуши, ошибки.
2. **`fcm-log-view.php?q=…`** — почему не генерился токен (`play_services` и

3. **`push-send-view.php`** — рассылки от 1С: кому ушло, кто подтвердил, кто

4. **`health.php`** — общее состояние: кроны, очередь, ошибки FCM.
5. В БД: `fcm_tokens WHERE device_uuid=…` (или `user_id=…`),
   `user_inbox WHERE user_id=…`, `push_send_recipient WHERE user_id=…`.

## 11. Правила поддержки (чтобы не сломать)

- **1С не трогаем.** Только вызываем её готовые методы (`getcontactid`,
  `binddevice`, `setpush`, `pushresult`).
- **Только добавляем, не ломаем существующее.** Любой новый шаг — через
  try/catch, чтобы падение не роняло старт.
- Новые серверные скрипты — **локальные переменные с префиксом**
  (`bs_`, `ib_`, …), иначе MODX затрёт.
- Миграции БД — **до** заливки PHP, руками в phpMyAdmin.
- Деплой сервера: `git commit` → `.\deploy.ps1` (scp). `.ps1` — только ASCII
  (Windows PowerShell 5.1 давится на кириллице).
- `workmanager` — версия **точная** (`0.10.9`), не `^`.
- Пуши всегда **data-only** — иначе headless-код не выполнится и ack/история
  сломаются.
