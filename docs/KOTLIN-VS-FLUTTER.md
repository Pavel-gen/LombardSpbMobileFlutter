# Что изменилось: Kotlin-приложение + старый сервер → Flutter 2.0.0 + новый сервер

Дата: 2026-09-02. Разбор «что было / что стало / какая дыра закрыта».

- Kotlin-исходники: `AndroidStudioProjects/LombardSpb/` (versionName 1.1, versionCode 6)
- Flutter: этот репозиторий (versionName **2.0.0**, versionCode **7**)
- Сервер: `Desktop/lombard-server/` (см. его `CHANGELOG.md` — полная хронология)

Пакет тот же — `best.app.lombardspb`. `device_uuid` в обеих версиях =
`Settings.Secure.ANDROID_ID`, при том же ключе подписи он **не меняется** →
привязка/история восстанавливаются с сервера после обновления.

---

## 0. Коротко

Kotlin-приложение и старый сервер работали по схеме «отправили пуш и надеемся».
Ни одна из проблем не отслеживалась, токены протухали молча, логин жил только
в памяти телефона, недоставленные пуши терялись навсегда.

Flutter 2.0.0 + новый сервер — это тот же UX, но с полной цепочкой надёжности:
durable-очередь, идемпотентность, подтверждение доставки, SMS-подстраховка,
серверный ящик уведомлений, тихое оживление токенов, фоновый воркер и
централизованный журнал ошибок. Плюс закрыты 3 конкретных UI-бага.

---

## 1. Клиент: Kotlin → Flutter

### 1.1. FCM-токен — главная дыра Kotlin-версии

| | Kotlin | Flutter 2.0.0 |
|---|---|---|
| Ротация токена (`onNewToken` / `onTokenRefresh`) | `NativePushService.onNewToken()` **только пишет токен в logcat**. На сервер НЕ отправляет. | `onTokenRefresh` → сразу `_sendTokenToServer()`. |
| Когда токен уходит на сервер | только из `MainActivity.onCreate` (а он открывается лишь по тапу на пуш или на «Наши услуги») + после выдачи разрешения на уведомления | при старте, при ротации, при возврате сети, из фонового воркера, по тихому пингу с сервера |
| Ретраи получения токена | нет — один `FirebaseMessaging.getInstance().token`, при ошибке `Log.w` | 6 попыток с нарастающими паузами (3с→10с→30с→90с→4мин), каждая неудача → диагностика на сервер |
| Ретраи отправки на сервер | нет — один `OkHttp enqueue`, при ошибке `Log.e`. Офлайн на старте = токен не дошёл в эту сессию | флаг `_tokenSentOk`, повтор при возврате сети и на следующем старте |
| Что шлётся с токеном | `token, platform, device_model, app_version, os_version, device_uuid` | + `user_id` (чтобы сервер мог сам снять пуши в 1С при удалении), `app_source:"flutter"`, `push_ack:true` |
| Реакция на сеть | нет | `connectivity_plus`: сеть появилась → добрать токен / повторить отправку |
| Фоновая проверка токена | **нет вообще** | `workmanager`: раз в ~24ч headless-задача берёт свежий токен → на сервер, синхронит ящик, выгружает журнал. Переживает закрытие и перезагрузку |
| Диагностика «почему нет токена» | нет | `google_api_availability` (статус Play Services) + модель/ОС/ошибка/стек → `fcm-log.php` |

**Итог:** в Kotlin-версии, если Google менял токен (переустановка, очистка
данных, ~год простоя, смена железа), сервер об этом никогда не узнавал и
продолжал слать на мёртвый адрес. Это и есть корневая причина «у коллеги
перестали приходить пуши». Во Flutter закрыто с пяти сторон.

### 1.2. Логин в персональные уведомления

| | Kotlin | Flutter 2.0.0 |
|---|---|---|
| Где хранится `phone_verified` | `SharedPreferences("app_prefs")` — **только локально** | локально + **сверка с сервером** через `bind-status.php` |
| Очистка данных приложения / «оптимизатор» MIUI стёр префы | пользователь разлогинен навсегда, пуши перестают ассоциироваться | при старте `bind-status.php` по `device_uuid` находит привязку → `phone_verified` восстанавливается автоматически |
| Экран «уже подключено» vs форма | по локальному флагу | сначала показывает последнее известное состояние (без мигания), потом тихо сверяется с сервером |
| Отвязка номера | `setpush(0)` в 1С + чистка префов | то же + `PushService.unregisterToken()` (удаляет FCM-токен и говорит серверу) — устройство перестаёт числиться получателем |

### 1.3. История уведомлений / пропущенные пуши

| | Kotlin | Flutter 2.0.0 |
|---|---|---|
| Хранилище | `SharedPreferences("push_history_prefs")`, только локально | локально + **серверный ящик `user_inbox`** |
| Пуш не дошёл (телефон был выключен, токен сдох, OEM зарезал фон) | потерян навсегда | лежит в ящике; при старте/возврате/пинге `syncInbox()` доливает пачкой за 90 дней |
| Дедупликация | нет — один пуш, придя дважды, двоился в списке | по `msg_id`: не двоится, даже придя и пушем, и из ящика |
| Сортировка | по порядку вставки | по времени события (для ящика — `created_at` с сервера) |
| Лимит | 200 | 200 (тот же) |

### 1.4. Подтверждение доставки (ack) — новое

Kotlin: **нет.** `Status = 1` в 1С означал лишь «FCM принял запрос».

Flutter: `_handleMessage` сразу (до показа уведомления, в т.ч. в headless-изоляте
на убитом приложении) шлёт `POST push-ack.php {msg_id, source}`. Нет ack за
20 минут → сервер говорит 1С слать SMS. Тап по уведомлению — тоже ack
(на случай, если headless не поднялся). Идемпотентно (локальный список
последних 300 `msg_id`).

### 1.5. UI-баги, которые чинили

| Баг | Kotlin | Flutter 2.0.0 |
|---|---|---|
| **Ссылки в тексте пуша не кликались** | на самом деле в Kotlin кликались (`Patterns.WEB_URL` + `Html.fromHtml` + `LinkMovementMethod`) — потерялось при первом переписывании | восстановлено: виджет `LinkifiedText` в диалоге пуша и в диалоге истории |
| **Длинный заголовок пуша ломал вёрстку истории** | `buildPushRow`: у `titleView` нет `maxLines` → длинный заголовок разъезжается | `maxLines: 2` + `TextOverflow.ellipsis`, дата под текстом, не в trailing |
| **Тёмная тема: чёрный текст на чёрном** | экран верификации форсил белый фон (`window.decorView.setBackgroundColor(WHITE)`), тёмной темы там не было | весь UI берёт цвета из `Theme.colorScheme` (`onSurface`/`onSurfaceVariant`), корректен в light и dark |
| Заголовок экрана «Подключение персональных уведомлений» обрезался | 22sp, «...» | укорочен до «Уведомления» — влезает |
| Мигание «форма ввода → ✅ подключено» при открытии | — (в Kotlin грузилось из локальных префов мгновенно) | Flutter добавил сетевую сверку → появилось мигание → починено: крутилка, потом состояние |

### 1.6. Умная маска телефона

Портирована 1:1: `PhoneMaskWatcher.kt` → `phone_mask_formatter.dart`. Та же
логика (нормализация `8→7`, код страны, закрывающая скобка на 4-й цифре,
курсор по числу цифр слева). Плюс покрыта unit-тестами (`dart test`).

### 1.7. Автоподстановка кода из SMS

`BroadcastReceiver`). Flutter: пакет `smart_auth` — то же самое, на iOS
код подставляет клавиатура (`autofillHints: [oneTimeCode]`).

### 1.8. WebView

Портировано: отклонение битого SSL (`handler.cancel()`), PDF → Google-вьюер,
кастомные схемы (банковские приложения) → `Intent`, офлайн-оверлей,
таймаут загрузки, реакция на пропажу/возврат сети, тап по пушу со ссылкой →
`loadUrl(link)`.

### 1.9. Экраны

| | Kotlin | Flutter 2.0.0 |
|---|---|---|
| Главный | 3 кнопки: Наши услуги / Калькулятор / Уведомления (+ бейдж числа непрочитанных) | + **Личный кабинет** → `https://lombard.center/onlajn-pogashenie/` |
| Калькулятор | оффлайн, зашитые цены за грамм | портирован 1:1 |

### 1.10. Наблюдаемость — новое

| | Kotlin | Flutter 2.0.0 |
|---|---|---|
| Логи | только `Log.d` в logcat — с телефона клиента недоступны | `AppLog`: кольцевой буфер событий → пачками на `app-log.php`, смотреть `app-log-view.php` по номеру/`device_uuid` |
| Необработанные ошибки | только авто-крэши AppMetrica | `runZonedGuarded` + `FlutterError.onError` + `PlatformDispatcher.onError` → каждая ошибка немедленно на сервер |
| Аналитика | AppMetrica (тот же ключ) | AppMetrica (тот же ключ — история не прерывается) + атрибут `app_source=flutter` |

### 1.11. Тесты

Kotlin: только шаблонные `ExampleUnitTest` / `ExampleInstrumentedTest`.

## 2. Сервер: старый → новый

Хронология и детали — `lombard-server/CHANGELOG.md`. Сводка.

### 2.1. Было (до 2026-08-31)

- `fcm-token.php`: наружу текли тексты исключений; `user_id` приводился к
  `(int)` — **GUID из 1С превращался в число**, связь токен↔клиент ломалась;
  upsert не снимал `disabled_at`.
- Чистка токенов: `DELETE ... WHERE id IN (...)` при **любой** ошибке отправки —
  выкашивало живые токены (у коллеги так удалили 3 из 5).
- Рассылка от 1С: запускалась фоновым процессом через `exec('php-cgi ... &')`,
  который при сбое запуска молча не отрабатывал целиком; параллельная отправка
  в FCM (`curl_multi`) под нагрузкой роняла часть сообщений.
- Нет: классификации ошибок FCM, диагностики генерации токена, логов рассылок,
  идемпотентности, ack, durable-очереди, reconcile-крона, health, heartbeat,
  dead-letter, bind-status, refresh-ping, inbox, app-log, защиты от гашения
  перевыпущенного токена.

### 2.2. Стало

| Область | Что добавлено | Закрывает |
|---|---|---|
| **Аккуратная чистка токенов** (`_fcm_tokens.php`, `fcm_cleanup.php`) | `fcmClassify()` (ok/unregistered/invalid/auth/transient/other); `fcmApplyResult()` — `disabled_at` вместо DELETE, гасим `stale` только при ≥10 ошибках И успех >3 дней назад; ночной hard-delete >30 дней | живые токены больше не удаляются по разовому сбою FCM/сети |
| **Диагностика токена** (`fcm-log.php`, `fcm-log-view.php`, `fcm_diag_log`) | приём + просмотр под паролем: Play Services, модель, ОС, ошибка, стек | «гадание на кофейной гуще», почему у части устройств нет токена |
| **`fcm-token.php` переписан** | не течёт ошибка; `user_id` не `(int)`; upsert снимает `disabled_at`, обнуляет `fail_count`; первый живой токен клиента → `setpush(1)` в 1С | сломанная связь токен↔клиент; «залипший» disabled |
| **Последовательная рассылка + полный лог** (`1c_send_push.php` переписан, `push_send_package`, `push_send_log`, `push-send-view.php`) | один процесс, по одному токену, `usleep(50мс)`, `set_time_limit(0)`; каждая отправка в БД и в файл; смотрелка под паролем | потеря части пушей из-за фонового процесса и `curl_multi` |
| **Подтверждение доставки** (`push-ack.php`, `push-reconcile.php`, `push_send_recipient`, `push_ack`) | приложение подтверждает `msg_id`; нет ack за 20 мин → `Status=0` → 1С шлёт SMS; поздний ack чинит `Status=0` → повторный `Status=1` | `Status=1` больше не значит «просто FCM принял»; недоставка реально уходит в SMS |
| **Защита от ложного SMS при ротации** (`fcmSetPushIn1C`, `fcmMaybeDisablePushIn1C`) | если любой токен клиента был активен <30 мин назад — `setpush(0)` придерживается (`SETPUSH_0_DEFERRED`); регистрация нового токена шлёт `setpush(1)` | пуш пришёл, но старый токен отдал `UNREGISTERED` → клиента ошибочно переводили на SMS |
| **Батч 1: durable + идемпотентность** (`push_outbox`, `req_hash`, `job_heartbeat`, `health.php`, dead-letter) | очередь получателей переживает падение процесса; повтор рассылки от 1С в пределах 90 сек отсекается по `sha256(тело)`; пульс кронов; `GET health.php` → 200/503 + `problems[]` | падение сервера в середине рассылки = потеря; дубль запроса 1С = двойной пуш+SMS; «крон молча умер» |
| **Батч 2: сервер — источник истины** (`bind-status.php`, `push-refresh-ping.php`) | «привязан ли номер» отвечает сервер по `device_uuid`; ночной тихий data-пуш `token_refresh` неактивным >3 дней токенам + отдельно «тёмным» клиентам `setpush(0)` | разлогин после очистки данных на MIUI; протухший токен у давно не заходившего пользователя |
| **Батч 3: журнал приложения** (`app-log.php`, `app-log-view.php`, `app_event_log`) | приёмник пачек событий + просмотр по номеру/`device_uuid`/`user_id` | с телефона клиента раньше нельзя было понять, что происходит |
| **Батч 4: серверный ящик** (`inbox.php`, `_inbox.php`, `user_inbox`) | воркер и `1c_send_push` пишут строку в ящик (идемпотентно по `user_id+msg_id`); приложение при старте забирает пропущенное | недоставленный пуш терялся навсегда |
| **1c_send_push → только очередь** (`push-outbox-worker.php` — основной отправитель) | 1С кладёт задание и свободна; рассыл + запись recipient/inbox + инлайн-отчёт делает воркер | связанность и хрупкость «всё в одном запросе» |

### 2.3. Мониторинг (было — ничего)

- `health.php` — БД, возраст heartbeat кронов, глубина очереди, застрявшие,
  dead-letter, ошибки авторизации FCM, доступность access-token FCM.
- `push-send-view.php` — рассылки от 1С: кому ушло, кто подтвердил, кто на SMS.
- `app-log-view.php` / `fcm-log-view.php` — по конкретному устройству.

## 3. Дыра → чем закрыта (сводная)

| Дыра (Kotlin / старый сервер) | Закрыта |
|---|---|
| `onNewToken` не шлёт токен на сервер | `onTokenRefresh` → сервер; + пинг + воркер + retry-on-resume + retry-on-network |
| Токен уходил на сервер только из WebView-экрана | шлётся при старте/ротации/сети/фоне/пинге |
| Нет ретраев ни при получении, ни при отправке токена | 6 попыток + повтор при сети + следующий старт |
| Токен без `user_id` на сервере | шлётся `user_id` → сервер сам снимает пуши в 1С при удалении |
| `DELETE` токена по первой ошибке | `disabled_at` + аккуратная политика + hard-delete через 30 дней |
| Логин только локально → разлогин на MIUI | `bind-status.php` восстанавливает по `device_uuid` |
| Недоставленный пуш теряется | `user_inbox` + `syncInbox()` за 90 дней |
| Дубль пуша в истории | дедуп по `msg_id` |
| «Отправили и забыли» (`Status=1` = «FCM принял») | ack + 20-мин окно + SMS-догонка + поздний ack |
| Дубль рассылки из 1С → двойной пуш+SMS | `req_hash` (sha256 тела, окно 90 сек) |
| Падение сервера в середине рассылки | `push_outbox` — durable-очередь, orphan-recovery |
| Ротация токена → ложный перевод клиента на SMS | сверка `sentToken` при гашении + придержка `setpush(0)` при недавней активности + `setpush(1)` при регистрации |
| `user_id` GUID → `(int)` на сервере | убрано приведение типа |
| Потеря пушей из-за фонового `php-cgi &` + `curl_multi` | последовательная отправка, один процесс, `set_time_limit(0)` |
| Ссылки в тексте пуша не кликабельны (после 1-го переписывания) | `LinkifiedText` |
| Длинный заголовок ломает вёрстку истории | `maxLines: 2` + ellipsis |
| Чёрный текст на тёмной теме | цвета из `colorScheme` |
| Нет фоновой проверки токена | `workmanager` раз в ~24ч |
| Нет логов с устройства клиента | `AppLog` → `app-log.php` |
| Нет мониторинга сервера | `health.php` (200/503) |
| «Почему у 69/1000 нет токена» — неизвестно | `fcm-log.php` + `google_api_availability` |

## 6. Риски переписывания (проверить перед релизом — см. RELEASE-CHECKLIST.md)

- **Ключ подписи** должен совпасть с текущим в Play (иначе `ANDROID_ID`
  сменится и восстановление привязки/истории не сработает).
- **Локальная история и `phone_verified` НЕ переезжают** (Kotlin писал их в
  отдельные файлы префов — `app_prefs`, `push_history_prefs`; Flutter пишет в
  `FlutterSharedPreferences`). Смягчение: `bind-status` восстанавливает логин,
  `inbox` доливает историю за 90 дней — **но только для привязанного номера**.
  Проверить на реальном обновлении Kotlin→Flutter.
- **iOS** — новое, в Kotlin не было. Отдельный прогон + APNs + App Store, если
  в scope.
- **`workmanager`** — на части OEM (Xiaomi/Huawei) периодическая задача может
  не срабатывать. Дублируется серверным пингом + inbox.
- **`user_inbox` хранит тела пушей 90 дней**, а там коды входа в ЛК — новая
  экспозиция относительно Kotlin (там история была только локальной). Решить
  политику хранения.
- Убрать `api_test.php` с прода; проверить, что сервис-аккаунт FCM не в git.
