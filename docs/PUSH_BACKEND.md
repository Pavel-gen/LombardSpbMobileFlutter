# Push-уведомления: что должен делать бэкенд

Клиент (Flutter-приложение) уже шлёт всё необходимое. Ниже — что нужно
поддержать на стороне `lombard.center/api`, чтобы закрыть пункты 3 и 4.

---

## 1. `POST /api/fcm-token.php` — регистрация токена (уже есть, расширено)

Тело запроса теперь содержит **`user_id`** и `app_source`:

```json
{
  "token": "<FCM token>",
  "user_id": "<из привязки номера, может быть пустым>",
  "platform": "android-14",
  "device_model": "Xiaomi 23021RAA2Y",
  "app_version": "1.0.0",
  "os_version": "14",
  "device_uuid": "<ANDROID_ID / identifierForVendor>",
  "app_source": "flutter"
}
```

Сервер должен: upsert по `token` (или по паре `device_uuid` + `platform`),
сохранять `user_id` и `updated_at = now()`. `user_id` нужен, чтобы при
удалении приложения (см. п. 3) можно было вызвать 1С `setpush(operation=0)`.

### `POST /api/fcm-token.php?action=delete` — явная отписка

Клиент вызывает это, когда пользователь сам отключает уведомления
(`PushService.unregisterToken`). Тело:

```json
{ "token": "...", "user_id": "...", "device_uuid": "...", "reason": "user_disconnect", "app_source": "flutter" }
```

Сервер: удалить строку токена; если `user_id` не пустой — вызвать
1С `setpush(operation=0)` для него.

## 2. Пункт 3 — «приложение удалили → снять получение пушей в 1С»

**Важно:** при удалении приложения на устройстве **не выполняется никакой код**
(ни Android, ни iOS). Поэтому «отправить запрос при удалении» технически
невозможно со стороны клиента. Единственный надёжный способ — серверный,
через ответ FCM при рассылке:

1. При каждой отправке пуша серверу приходит ответ по каждому токену.
   Токены удалённых приложений возвращают:
   - HTTP v1 API: `UNREGISTERED` (`404`) или `INVALID_ARGUMENT` (`400`) с
     `errorCode: "UNREGISTERED"`;
   - legacy API: `"error": "NotRegistered"` или `"InvalidRegistration"`.
2. Получив такой ответ для токена:
   - удалить токен из своей БД;
   - если у токена был `user_id` — вызвать 1С `setpush(operation=0)` для него
     (тот же вызов, что делает кнопка «Отключить» в приложении).
3. Дополнительно (необязательно, но полезно) раз в N дней прогонять все
   токены через «dry run» отправку и чистить мёртвые так же.

Клиент со своей стороны помогает максимально:
- шлёт `user_id` вместе с токеном — серверу есть кого отвязывать;
- при `onTokenRefresh` присылает новый токен (старый после этого можно
  считать мёртвым и удалять);
- при явном отключении вызывает `?action=delete` и `deleteToken()`.

## 3. Пункт 4 — почему на части устройств не генерируется FCM-токен

### `POST /api/fcm-log.php` — приёмник диагностики (нужно создать)

Клиент шлёт сюда JSON на **каждой неудачной попытке** получить токен и один
раз при «выздоровлении» (`note: "recovered"`). Достаточно писать тело в
таблицу/файл как есть. Пример полезной нагрузки:

```json
{
  "stage": "fcm_token",
  "attempt": 2,
  "ts": "2026-08-31T09:12:44.001Z",
  "app_source": "flutter",
  "device_uuid": "…",
  "app_version": "1.0.0",
  "build_number": "1",
  "platform": "android",
  "os_version": "13",
  "sdk_int": 33,
  "device_model": "HUAWEI STK-L21",
  "brand": "HUAWEI",
  "is_physical_device": true,
  "supported_abis": ["arm64-v8a"],
  "google_system_features": [],
  "authorization_status": "authorized",
  "auto_init_enabled": true,
  "error_type": "FirebaseException",
  "error": "[firebase_messaging/unknown] SERVICE_NOT_AVAILABLE",
  "error_code": "unknown",
  "error_plugin": "firebase_messaging",
  "error_message": "SERVICE_NOT_AVAILABLE"
}
```

### Как читать логи

- `error_message: "SERVICE_NOT_AVAILABLE"` / `AUTHENTICATION_FAILED` /
  `MISSING_INSTANCEID_SERVICE`, `google_system_features` пустой,
  `brand: HUAWEI` — **на устройстве нет/сломан Google Play Services**.
  Лечится только на устройстве (обновить GMS, вход в Google-аккаунт).
  Для таких устройств пуши FCM в принципе недоступны.
- `platform: ios`, `apns_token_error` заполнен / `apns_token_present: false` —
  не выдаётся APNS-токен: нет прав на уведомления, не настроен APNS-ключ в
  Firebase, либо сборка без push-entitlement.
- `authorization_status: "denied"` — пользователь запретил уведомления;
  токен на Android всё равно должен выдаваться, на iOS — нет.
- Ошибок нет, но `attempt` доходит до 5 — таймауты сети; обычно
  «вылечивается» само на `note: "recovered"` при следующем запуске.

### Что уже усилено в клиенте (`lib/services/push_service.dart`)

- `setAutoInitEnabled(true)` перед запросом токена;
- получение токена вынесено из старта приложения в фон (старт не блокируется);
- до 6 попыток с нарастающими паузами (3с → 10с → 30с → 90с → 4мин);
- на iOS перед `getToken()` дожидаемся APNS-токена;
- повторная попытка при каждом возврате приложения на передний план, пока
  токена нет;
- каждая неудача логируется локально (`[PushService]` в logcat/flutter logs)
  и уходит на `fcm-log.php`.

## 4. Подтверждение доставки пуша (push-ack) — сделано; надёжность усилена 2026-09-04

Клиент (`lib/services/push_service.dart`):
- шлёт `"push_ack": true` в `POST /api/fcm-token.php`;
- читает `data.msg_id` из входящего пуша;
- на приём сообщения (foreground / headless / тап) шлёт
  `POST /api/push-ack.php {"msg_id": "...", "source": "..."}`;
- **ack не fire-and-forget:** если POST не прошёл, `msg_id` лежит в очереди
  `pending_acks` (SharedPreferences) и до-сылается при старте / возврате в
  приложение / появлении сети / `syncInbox()` / фоновом воркере. Дедуп по
  `acked_msg_ids` (300 последних) + по самой очереди.

### Что делает бэкенд (реализовано, см. `lombard-server`)

1. `fcm-token.php` — поле `push_ack` → `fcm_tokens.push_ack` **и**
   `ack_declared` (монотонный: раз 1 — навсегда). По `ack_declared` рассылка
   решает, ждать ли ack от устройства.
2. Payload рассылки несёт `msg_id` (+`id_send`). `push_send_recipient` хранит
   `push_attempts`, `last_push_at`, `next_check_at`.
3. `push-ack.php` — `{msg_id, source}` → `acked_at = NOW()`, `status_final = 1`,
   `next_check_at = NULL`, `ack_declared = 1`. Всегда `{"status":"ok"}`.
4. `push-reconcile.php` (крон раз в минуту) — по строкам `status_final IS NULL
   AND acked_at IS NULL AND next_check_at <= NOW()`:
   - `push_attempts < 4` → **повторная отправка пуша**, `next_check_at` через
     5 / 10 / 20 / 30 мин (растёт);
   - `push_attempts = 4` → `status_final = 0` (`ack_timeout`) → в 1С `Status = 0`
     → SMS-догонка.

   «Замка» (`push_ack_locked_until`) больше нет: устройство, не подтверждающее
   доставку, — это честная недоставка → SMS, а не повод молчать 7 дней.

## 5. Авто-включение пушей по `device_uuid` при входе в приложение — сделано в клиенте 2026-09-04

Раньше `bind-status.php` использовался только чтобы «не разлогинивать» при
потере локальных префов. Теперь это же и штатный путь **быстрого включения**:
при открытии экрана «Уведомления» (и на старте приложения) клиент, ещё до
формы ввода номера, шлёт `POST bind-status.php {device_uuid, token?}`. Если
сервер ответил `bound:true` — экран сразу переключается в подключённое
состояние **без повторного ввода номера и кода из SMS**.

Новое в клиенте: сразу после такого восстановления привязки клиент
до-регистрирует текущий FCM-токен (`POST fcm-token.php` уже с `user_id`),
не дожидаясь следующего запуска. От бэкенда по-прежнему нужно только то,
что уже описано в п. 1 и в `bind-status.php`:

- в ответе `bind-status.php` возвращать номер для показа на экране («на этом
  устройстве зарегистрирован номер …»). Клиент показывает номер **без маски**,
  поэтому нужен **полный `phone`** (`+79991234567`); поле `phone_mask`
  (`+7•••95`) остаётся как запасной вариант, если полного нет. Без любого из
  них на переустановленном устройстве строка с номером просто не покажется
  (сам факт «подключено» и кнопка «Отписаться…» — покажутся);
- `fcm-token.php`: upsert по `device_uuid`, при первом живом токене клиента —
  `setpush(1)` в 1С (как и раньше).

### Принудительное обновление токена со стороны сервера

Вопрос: если у устройства протух FCM-токен — можно ли с сервера заставить
его обновиться? Ответ: да, пока на устройство ещё доходит хоть какой-то пуш.

1. **Тихий пинг `token_refresh`** (уже есть, `push-refresh-ping.php`) —
   data-only пуш `{"type":"token_refresh"}` без title/body. Клиент в
   headless-изоляте делает `getToken(force)` и присылает свежий токен на
   `fcm-token.php`. Без уведомления, без ack.
2. **Флаг `refresh_token` в обычной рассылке** (новое в клиенте 2026-09-04) —
   если в `data` любого контентного пуша положить `"refresh_token":"1"`,
   клиент, помимо показа сообщения, в фоне перерегистрирует токен. Удобно,
   когда сервер видит деградацию доставки, но пуш пока проходит.

**Ограничение.** Единственный канал сервер→устройство — это FCM push,
адресуемый **по токену**. `device_uuid` серверу «не позвонить». Если токен
уже полностью мёртв (переустановка, очистка данных, ~год простоя) —
достучаться пингом нельзя. На этот случай работают: ежесуточный
`workmanager` в приложении (сам переотправляет токен), перерегистрация при
каждом открытии приложения, серверный `inbox` (донесёт сообщения при
следующем запуске) и SMS-догонка от 1С.
